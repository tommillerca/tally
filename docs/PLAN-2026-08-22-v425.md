# The big-batch plan (18 items, 2026-08-22)

Source: docs/FEEDBACK-2026-08-22-v424.md, item numbers below refer to it.
Status: DRAFT, awaiting Tom's approval per workstream. Nothing builds until the
workstream is approved. The grill section at the bottom attacks this plan's own
weak points and is part of the deliverable.

Sorting principle: player-visible pain first (bugs, perf), then reworks that
need Tom's eye (options and mockups), then new features. Each release stays
small enough that the gate and a live check can actually vouch for it.

## WS1 - Bug batch (target: v425, no design input needed)

Root causes below were read from the code today, not guessed.

**1a. Saved fit forgets almost everything after Take-it-all-off (item 16).**
Root cause FOUND: a fit stores `tm` (transmog overrides) + `cos` (non-gear
cosmetics) and deliberately excludes gear ("a fit is a LOOK, never stats",
js/loot.js:1634). That contract was written when strip was cosmetics-only. Now
that Take-it-all-off empties gear slots too (v424), applyFit's transmog writes
land on EMPTY gear slots, and equipped() only honours a transmog on a slot that
holds something. So the look silently vanishes for every gear slot and only the
plain cosmetics come back: "only remembered a couple things", exactly.
Fix: fits capture the gear loadout ids too; applyFit re-equips each piece the
player still owns (skip sold ones, same as cosmetics). This also restores the
stats, which matches the player's mental model of "my old fit". Existing saved
fits have no gear map; they keep today's behaviour until re-saved, and the
wardrobe hints to re-save (one line, not a migration).

**1b. Wheel text upside down on device (item 13).**
Root cause FOUND: labels "ride the same rotate() transform" as their wedge
(js/wheel.js:86), so wedges in the bottom half render inverted text. Fix:
counter-rotate any label whose final angle sits in the 90-270 band so all text
reads upright. Pixel-verify on the rendered wheel at several landing angles.

**1c. Day-strip black hole (item 2, last part).**
Root cause FOUND: renderToday guards the hero, quests, banners, wellness and
kitchen behind `isToday` (js/app.js:3581-3675), so tapping a past day strips
the screen to bones with nothing saying how to get back. Fix: past days keep
the frame (header + day strip stays put, obviously) and gain a pinned "Back to
today" pill; the history view reads as "you are looking at Tuesday", not "you
broke it". No data-flow change, just what the past-day render keeps.

**1d. Crew card pets cropped by long titles (item 5).**
Long title/nickname wraps, the bottom banner grows, the pet gets eaten.
Fix: fixed banner height on the album card; title ellipsizes or auto-shrinks
one step, never wraps into the art. Verify with the worst real case ("Bone
Grand Master 113" + nickname) by measuring the rendered card.

**1e. Banner icon pinned top-left instead of centered (item 7).**
"Thanks for being early" (js/app.js:2058) and the first-step foot share a
banner skin whose icon slot is top-aligned. Fix at the shared skin so every
current and future banner centers its icon. Check all existing banners after.

**1f. Gwart crate nag (item 17).**
The bag picker (gwartPool) weights an unopened crate so heavily it dominates.
Fix: the crate reminder fires at most once per app open; after that the crate
context drops out of the pool for the session.

**1g. Wanderer in the lake (item 15).**
Root cause: wandererAt is pure math on the cell grid (js/wanderer.js:170), no
land awareness at all. Fix needs a water oracle: test the spawn center against
the basemap's water polygons, and on water, walk a deterministic sequence of
fallback offsets (same seed) until land; if the whole cell is water, no
wanderer that lap. Risk flagged in the grill: the oracle must give the same
answer on every device or two friends see him in different places. Recon step
before code: confirm we can query water polygons from the vector tiles at a
point that is off-screen, and quantize the test so devices agree.

**1h. Double-tap tab actions (item 14).**
Today tab double-tap scrolls to top; Boneyard tab double-tap (while already in
it) recenters + zooms to the player. Guard so the first tap of a double never
also triggers a re-route.

**1i. Remove "Start with breakfast", pin quests under the 4 chips (item 2,
first part).** The button is the topNudge at js/app.js:17225. Cheap, does not
wait for the WS3 rework, and WS3 inherits the new order as its baseline.

**1j. Background into the dynamic island (item 8).**
viewport-fit=cover is already set and --sat exists (app.css:62). Fix: the game
background paints behind the status bar / island instead of stopping at the
safe-area line; content keeps its safe-area padding. Verify on-device (the
simulator has the island, use it).

## WS2 - Performance release (target: v426, ships ALONE)

**2a. Sluggish on bad connection + reload-on-return (item 18).**
Root cause FOUND: the service worker serves the ENTIRE app shell network-first
with `cache: 'no-cache'` (sw.js:296), so every js/css/html file waits for the
real network on every load. On a bad connection that is the whole symptom, and
when iOS evicts the page after a minute away, the reload pays it all again.
Fix: versioned atomic app shell. Install precaches the complete version (the
PRECACHE list already exists); when a complete version is cached, the shell is
served cache-first INSTANTLY and the SW revalidates one small version stamp in
the background; a new deploy downloads fully in the background and swaps
atomically on next open. Never mixes files from two versions (the class of bug
network-first was protecting against). This is the riskiest change in the plan
(a bad SW can strand every player) so it ships alone, with the sw-upgrade-audit
extended to cover: fresh install, upgrade mid-session, bad-network boot
(throttled), one-file-404 during deploy, and the killswitch path.

**2b. Wordmark jolty on overscroll (item 1).**
Measure first on device: is it scroll-event JS quantized by the 130ms
transition, or paint cost? Then fix on the compositor (scroll-driven transform,
no transition mid-scroll). Small, but it rides the perf release so the
before/after is measured once.

**2c. Tab-swap frozen frame (carried from v424).** The named next lever:
150-250ms of old screen before swap (render + decode). Same release, same
measurement pass.

## WS3 - Today screen rework (item 2, options for Tom, then mockups)

Baseline after WS1: hero, 4 chips, quests, then the rest. The rework question
is what "the rest" is. Three options, pick one (or a hybrid), then MOCKUPS
before any code:

**Option A - The Daily Log.** Everything below quests merges into ONE carded
ledger owned by the day: macros ring at its head, then meals, wellness ticks,
health, sign-off as rows of the same card. One anchor, one header, one visual
container. Strongest fix for "floating widgets", biggest relayout.

**Option B - Summary bar + uniform sections.** A compact pinned strip right
under quests (calorie ring, streak, wellness dots) that condenses on scroll;
below it the existing sections stay separate but get ONE shared card skin,
spacing rhythm and header style so they read as siblings, not strangers.
Cheapest, keeps current data flow, mostly CSS + ordering.

**Option C - Two zones.** Explicit "Game" zone (hero, chips, quests) and
"Body" zone (macros, meals, wellness, health) with distinct zone headers and a
visual seam, leaning into the RPG/health split the app already implies.
Middle cost, strongest identity, risks feeling like two apps.

My recommendation: B now, and it does not foreclose A later. A is the best
end-state but is the most regression-prone screen in the app (day-strip, scroll
preservation, banner queue all live here) and B delivers the "anchored" feeling
for a fraction of the risk. Mockups for whichever Tom picks.

## WS8 - The Walk Potion (item 9, design doc before any code)

Precedent research: Pokemon GO's real analogue is ADVENTURE SYNC (rewards from
HealthKit/Google Fit steps while the app is closed), closer than the GO Plus
autocatcher (a Bluetooth device we cannot be). Design sketch to be grilled in
its own doc:
- Cook a potion in the kitchen (herb cost = real herb sink), drink to open a
  15-minute window. App closed, player walks.
- On next open, the game reads steps/distance covered during the window
  (HealthKit on the native build; PWA fallback is time-capped accrual at the
  same ceiling so web players are not second-class) and rolls coins + herbs
  ONLY. No bosses, no wanderer, no crates, hard daily cap.
- Window expiry forces the return trip and another cook: the loop Tom wants.
Deliverable: design doc with the economy numbers and the anti-cheese story,
approved before a line of code.

## The grill (where this plan is weakest)

**G1. The SW rework can strand players.** A bad service worker is the one bug
that survives a fix being deployed, because the broken SW decides whether the
fix is ever fetched. This is why WS2 ships alone, keeps a killswitch (a tiny
version-stamp endpoint the SW always checks network-first; flipping it forces
full re-download), and extends sw-upgrade-audit to red on: stranded-on-old,
mixed-version module graph, and killswitch-ignored. If the audit cannot be
made to go red on a deliberately broken SW, the change does not ship.

**G2. The wanderer water oracle may disagree across devices.** Vector-tile
water polygons at different zooms can classify the same point differently. If
devices disagree, friends see different wanderers, which is worse than the
lake. The recon step must PROVE same-answer-everywhere (quantized test at a
fixed zoom's tile data) before the fix is attempted; if it cannot, fallback
design: the wanderer stays as-is but gains a rowboat sprite over water. Joke,
but only half: art-side fixes are on the table if the data-side is unsound.

**G3. WS3 touches the most regression-prone screen in the app.** Day-strip,
scroll preservation, the banner queue, and Gwart all live on Today. That is the
argument for option B (reskin + reorder, no data-flow rewrite) and for mockups
before code. If Tom picks A, it gets its own release and a full regression
pass, not a shared one.

**G4. Paywalled cheers can read as paywalled kindness.** The mitigation is
structural, not cosmetic: free cheers stay unlimited and visible-first, premium
is presentation only, and nothing a premium cheer does affects any number in
the receiver's game. Also flagged: IAP on the native build must stay inside the
cosmetic-only decision of 2026-08-07.

**G5. The potion has a two-class problem.** HealthKit-backed accrual on native
vs a time-capped fallback on PWA means two different feels for one mechanic.
The design doc must settle whether the fallback is generous enough to be fair
or whether the potion is honestly badged as "best with the app installed".
Settling it in the doc is cheap; discovering it in reviews is not.

**G6. Friend paddocks share new data.** Pet roster + wear moves from
device-local to crew-visible. It is the point of the feature (showing off),
but the plan says it out loud: this is the first time pets leave the device,
it rides the plaintext social payload (never the E2E vault), and visibility is
crew-only.

**G7. Sequencing is my guess at Tom's priorities.** Bugs and perf first is
defensible, but if retention is hurting, the potion (WS8) and cheers (WS6) are
the retention levers and could jump the queue. Tom's call, and the plan is
ordered so reshuffling releases does not create dependencies. Only hard edge:
WS1 before WS3 (the rework builds on the new baseline).
