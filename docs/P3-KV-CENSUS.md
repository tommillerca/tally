# P3 kv restore census, 2026-09-07

Scope: this checkout's js/db.js importAll, with readers/writers traced across js/*.js. The importer has no key allowlist: **every nonempty string key** carrying a `v` is writable, including arbitrary unknown keys. A finite list alone cannot enumerate that domain. The table enumerates all current literal call keys, indirect constants, generated families, and historical names in DEVICE_KV/QUIET_KV, followed by the exhaustive unknown-key rule. Source references are checkout-relative. This census is not an authenticity or security certification.

`Payload-wins` below describes replace:false unless stated otherwise. Replace:true intentionally clears each declared store and restores its snapshot, including earned state absent from that older snapshot. It is an explicit rollback, not a monotone merge. Omitted stores stay untouched; P3 rejects present null/non-array stores. Existing device-key exceptions and higher day ceilings are recorded below. P3 rejects duplicate/nonstring kv keys before mutation; otherwise unknown keys/fields remain intact. Unknown keys can still be cleared by a deliberate replace whose kv snapshot omits them.

P3 adds limited known-container/type validation, not a full recursive schema. Nullable values keep legacy fallback behavior. Accepted nested values can still be hostile. The rejection distinguishes damaged/unsupported state and leaves all seven stores unchanged; it never silently coerces a future container to an empty one. The map/array/number lists live beside validateRestoreKv in js/db.js. Arrays of unknown pet rows remain opaque and are not discarded.

## Future build contract: what actually happens

1. `exportAll.version` is **database schema version 3**, not app build v513. `pushBackup(appV)` sends appV as outer request metadata, but `pullBackup` does not use appV to decide data compatibility. A newer build retaining schema 3 is accepted today. A higher database version is already refused before any store changes; this was not a P3 invention.
2. Unknown kv keys and unknown pet rows can survive import/export byte-for-byte. P3 guards that round trip and fixes unsupported equipped iid loss on opening. The raw Dressing Room reader retains unresolved non-pet ids for its existing explanatory panel. It also keeps opaque equipped fields when loot's equip, equipGear and pet slot repair write a different slot. The rendering projection only exposes known matching art and a known pet species, through the existing isKnownPet helper.
3. P3 refuses known future pet bank markers (`petLvlV > 2`, `pettalents.__iidV > 2`) at import. This is a safe refusal, not forward interpretation. It does not protect an older binary's every reader when opening an already-populated database; an import boundary cannot intercept those reads.
4. The universal house rule is **not satisfied**. Measured: `foodbuffs:[{kind:'future-aura',charges:9,format:4}]` lands intact under schema 3, then `activeFoodBuffs()` deletes it on read. The subsequent export contains zero buff rows. The new restore-debt audit stays red for this exact defect. Fix requires js/cooking.js, outside lane ownership: prune only understood expired kinds, retain unknown rows in storage, expose only understood live rows to gameplay, and apply the same policy to every buff writer. A coordinated backup/build compatibility policy is still needed for unknown top-level stores and other future nested formats.
5. Cloud conflict retry already pulls before retrying a 409 and refuses the retry when import fails. That is not a blanket guarantee that every older writer cannot overwrite a newer same-schema blob. No Worker or live-cloud proof was run.

## Measured unresolved merge defects and proposed coordinated changes

`restore-debt-audit.mjs` has a healthy CONTROL and four deliberately failing end-of-chain checks. These are active PURE entries, not ignored assertions or tests of the broken behavior as expected behavior.

- `petInst`: earned same-species duplicate disappears, 2 copies to 1. Add iid deletion receipts to every salvage/remove/breed/extinction path, retain unseen live instances by iid on merge, and filter tombstoned iids before any reclaim migration. A plain union revives intentionally consumed instances and is not a safe fix.
- `petLvlSteps`: real petStepsForIid answer falls 1000 to 10. Coordinate bank format migration, per-iid earned step merge and petStepCredit with instance membership. A bare maximum is unsafe across species/iid schemas and independently credited steps.
- `potions`: persisted spent count 0 becomes 1 after old blob merge. Add revision/receipt tracking to grantPotion, drinkPotion, transmute, reward writers and importer in one coordinated economy change. The cooking writers are outside this lane; max refunds spends and min loses earnings.
- Future `foodbuffs`: opening deletes one earned opaque row. Exact cooking-reader proposal is above.

Other risks in the table are source-traced hypotheses or policy gaps, not measured exploit claims. No universal winner is inferred for flags, timestamps, currencies without revisions, or queues with deletions. The existing import pre-reads local kv before its write transaction, so concurrent gameplay/import can still race; P3 does not claim cross-tab serializable merging.

## Census method and coverage limits

Scanned every literal kvGet/kvSet/kvUpdate/kvBump/kvBumpRevisioned call in js/*.js, then traced indirect arguments (`INIT_CURSOR`, `GIFTBOX`, `KV`, retirement/grant/intro constants), db.addIfAbsent/claimAndPay and atomic pay.kv writers, and generated key expressions. Also included historical names from js/db.js's quiet/device taxonomies. Numeric currency revision keys are written indirectly by payout builders. The importer itself can store keys no current callsite names, covered by the final wildcard row. LocalStorage, native keychain keys, xp ledger ids and `newsSeen` entry ids are separate domains, not omitted kv rows.

This table intentionally records per-key policy even when multiple keys share the same risk. It does not claim every nested property has been validated. Browser rendering and remote authority remain independent reviewer proofs.
